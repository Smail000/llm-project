# План работ: 3 человека, 3 коммита

Модули делятся на три части: **граф**, **поиск** и **агент**. Участники работают независимо, все в ветке `main`, и каждый делает один коммит под своим именем.

| Участник | Часть | Файлы | Требования |
| --- | --- | --- | --- |
| 1 | Граф | `extraction.py`, `graph_builder.py`, `communities.py` | FR-1, FR-2, FR-3 |
| 2 | Поиск | `search.py` | FR-4, FR-5, FR-10 |
| 3 | Агент | `tools.py`, `agent.py` | FR-6 – FR-10 |

## Почему можно работать независимо

- **Интерфейсы между частями уже заданы** в `src/assistant/infra/schemas.py`, их никто не меняет:
  - граф отдаёт поиску `nx.DiGraph`: узлы с атрибутами `type`, `name`, `sources`, рёбра с `type`, `weight`, `sources`, плюс список `Community` со сводками;
  - поиск отдаёт агенту `Answer` с полями `text`, `sources`, `facts`, `refused`;
  - агент вызывает поиск через `local_search` и `global_search` с готовыми сигнатурами.
- **У каждой части свои контрактные тесты** на маленьком графе из `tests/contract/conftest.py`, с подставной моделью и подставной ERP. Чужой код и Ollama для них не нужны.
- **Файлы не пересекаются**, поэтому при `git pull` конфликтов не будет.

## Правила работы в `main`

1. Перед началом: `git pull`.
2. Меняете только свои файлы. Остальные файлы репозитория и сигнатуры функций не трогаете.
3. Вспомогательные функции и новые файлы добавляете только внутри своей папки: `src/assistant/graphrag/` или `src/assistant/agent/`.
4. Часть готова, когда проходят её контрактные тесты и `make lint`.
5. Коммит под своим именем:

   ```bash
   git config user.name "Имя Фамилия"
   git config user.email "почта@example.com"
   ```

6. Перед пушем: `git pull --rebase`, затем `git push`. Файлы разные, поэтому rebase пройдёт сам.
7. Папку `artifacts/` в свой коммит не добавляете. Её коммитит тот, кто пушит последним (см. «Финальный шаг»).

## Договорённость между участниками 1 и 2

Качество режима global зависит от сводок сообществ, а контрактные тесты это не проверяют. Если в сводке нет готовых чисел, global-поиск не ответит на обзорные вопросы вроде «Какой узел чаще всего отказывает в линейке „Арктика“?».

Договоритесь заранее: `summarize_community` передаёт модели подсчёты, посчитанные кодом:

- отказы узлов по линейкам (сумма весов рёбер `FAILED`);
- отказы по моделям;
- снятые с производства детали (`REPLACED_BY`) и модели, в которых они стоят.

## Участник 1 — Граф (FR-1, FR-2, FR-3)

**Файлы:** `src/assistant/graphrag/extraction.py`, `graph_builder.py`, `communities.py`

### Задачи

1. **`extract_chunk`.** Промпт описывает схему с направлением каждой связи и содержит пример. Модель вызывается с `json_schema=EXTRACTION_SCHEMA`. Разбор JSON, одна повторная попытка, после второй неудачи пустой результат. Имена приводятся к каноническому виду через `canonical_name`. Коды, которых нет в тексте чанка (`find_codes`), и названия не из словаря отбрасываются, связь с отброшенным концом тоже. Число отброшенных пишется в `dropped`.
2. **`build_graph`.** Узел `Type:name` с атрибутами `type`, `name`, `sources`. Ребро с атрибутами `type`, `weight` (число разных чанков) и `sources`. Связи проверяются через `Relation.matches_schema()`. Встречные `REPLACED_BY`: остаётся связь с большим весом, при равенстве удаляются обе. Число конфликтов пишется в `graph.graph["conflicts"]`.
3. **`detect_communities`.** Алгоритм Лувена (`nx.community.louvain_communities`) на неориентированной копии графа с учётом `weight` и фиксированным `seed`. Номера сообществ идут с нуля.
4. **`summarize_community`.** Код считает числа по весам рёбер (см. договорённость выше) и передаёт их модели готовыми. Один вызов модели, сводка обрезается до 150 слов.

### Проверка

```bash
make test ARGS=tests/contract/test_extraction_and_graph.py
make test ARGS="tests/contract/test_communities_and_search.py -k 'not local_search and not global_search'"
make lint
```

С моделью можно проверить свою часть отдельно: `make eval-extraction` и `make index`.

### Коммит

```bash
git add src/assistant/graphrag/extraction.py src/assistant/graphrag/graph_builder.py src/assistant/graphrag/communities.py
git commit -m "feat: извлечение, граф знаний и сообщества (FR-1–FR-3)"
git pull --rebase && git push
```

- раздел 2: как устроены извлечение, граф и сообщества
- раздел 3: Precision и Recall извлечения, число отброшенных связей, стоимость индексации

## Участник 2 — Поиск (FR-4, FR-5, FR-10)

**Файл:** `src/assistant/graphrag/search.py`

### Задачи

1. **`local_search`.**
   - Опорные сущности ищутся через `find_codes` и `find_names`, без модели.
   - Если кода из вопроса нет в графе или опорных сущностей нет, функция сразу возвращает `Answer(..., refused=True)`, модель не вызывается.
   - Если опорных сущностей две и больше, берутся рёбра на всех путях длиной до 3 связей между ними, направление при поиске пути не учитывается (`to_undirected`, `all_simple_paths`). К ним добавляются цепочки `REPLACED_BY` от деталей на путях.
   - Если опорная сущность одна, берётся её окрестность на глубину 2.
   - Модель получает пронумерованные факты вида `E-17 -INDICATES-> пусковое реле`, не больше 8000 символов. Если в фактах есть замена, ответ называет последнюю деталь цепочки.
   - `sources` — документы, а не чанки: `chunk_id.split("#")[0]`.
2. **`global_search`.**
   - Шаг map: для каждой сводки один вызов с `json_schema=MAP_SCHEMA`. Нечитаемый частичный ответ пропускается.
   - Шаг reduce: частичные ответы с `score > 0` объединяются одним вызовом.
   - Если таких ответов нет, функция возвращает `refused=True`.

### Проверка

```bash
make test ARGS="tests/contract/test_communities_and_search.py -k 'local_search or global_search'"
make lint
```

### Коммит

```bash
git add src/assistant/graphrag/search.py
git commit -m "feat: локальный и глобальный поиск по графу (FR-4, FR-5)"
git pull --rebase && git push
```

### В отчёт

- раздел 2: как устроены два режима поиска
- раздел 3: таблица режимов по типам вопросов и по стоимости
- раздел 4: два разобранных примера — где граф выигрывает и где уступает

## Участник 3 — Агент (FR-6 – FR-10)

**Файлы:** `src/assistant/agent/tools.py`, `agent.py`

### Задачи

1. **`TOOL_SCHEMAS`.** Пять инструментов в формате function calling: `search_knowledge`, `summarize_topic`, `check_stock`, `get_price`, `create_service_order`. Параметр `warehouse` задан перечислением `["Москва", "Санкт-Петербург", "Казань", "Новосибирск"]`.
2. **`build_tools`.** Аргументы проверяются до обращения к ERP: склад из списка, номер детали вида `P-1042` или `P-1042B`, количество больше нуля. `ErpNotFound` и `ErpRejected` возвращаются как `{"error": ...}` с разным текстом. `ErpUnavailable` пробрасывается дальше: повторы делает агент.
3. **`run_agent`.**
   - Цикл с моделью, ей передаётся `TOOL_SCHEMAS`, не больше `max_steps` вызовов инструментов, каждый вызов записывается в `steps`.
   - Неизвестный инструмент и аргументы `_raw` возвращаются модели как ошибка.
   - Номер детали должен встречаться в вопросе или в результатах прошлых инструментов. Иначе вызов отклоняется, а модель получает подсказку вызвать `search_knowledge`.
   - Количество в заказе должно быть названо в вопросе, иначе агент задаёт уточняющий вопрос.
   - Повторный вызов с теми же аргументами получает прежний результат.
   - При `ErpUnavailable` вызов повторяется ещё два раза. После трёх неудач ответ сообщает, что данные ERP получить не удалось.
   - При `confirm=False` агент возвращает `needs_confirmation=True` и `pending_action`. При `confirm=True` заказ создаётся, его номер попадает в ответ.
   - Перед ответом коды и числа сверяются с вопросом и результатами инструментов. При расхождении одна попытка исправления, после второй — отказ.
   - Когда данных нет, ответ пишет «в базе знаний не найдено» и возвращает `refused=True`.

### Проверка

```bash
make test ARGS=tests/contract/test_tools_and_agent.py
make lint
```

Повторы при отказе ERP проверяются так: в `.env` поставить `ERP_FAIL_RATE=0.3` и перезапустить `make up`.

```bash
git commit -m "feat: инструменты и агент (FR-6–FR-10)"
git pull --rebase && git push
```

## Финальный шаг: прогоны и отчёт

Прогоны на настоящей модели возможны только тогда, когда в `main` есть все три части. Финальный шаг выполняет тот, кто пушит **последним**. Результаты он добавляет в свой коммит, поэтому коммитов остаётся три.

1. `git pull`, чтобы получить код двух других участников.
2. Прогоны:

   ```bash
   make test
   make lint
   make index
   make ask MODE=local Q="Какую деталь заказать при ошибке E-17 на AR-210?"
   make ask MODE=agent
   make eval-all
   make eval-extraction
   ```

   Ожидаемый результат: в ответе local названа P-1042B, а в источниках есть `bulletin_SB-2025-03.md`. В ответе agent — P-1042B, остаток 3 шт. в Казани и цена 2630 руб.
3. Цифры из `artifacts/eval_*.json` и `index_stats.json` переносятся в отчёт, отчёт сохраняется как `REPORT.pdf`.
4. В свой коммит добавляются `artifacts/` (вместе с `llm_cache/`) и `REPORT.pdf`. После пуша ставится метка:

   ```bash
   git tag v1.0
   git push --tags
   ```
